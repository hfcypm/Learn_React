# TypeScript 学习评估与验收标准

**目标**：通过概念、编码、排错和项目评审确认类型系统是否真正用于解决问题。

## 1. 阶段考核

### 阶段一：基础

- 解释类型推导、类型注解和类型断言的区别。
- 使用接口、类型别名、联合类型和函数类型建模业务数据。
- 配置 strict 模式并修复基础类型错误。
- 将 5 个 JavaScript 工具函数迁移为 TypeScript。

### 阶段二：进阶

- 使用泛型编写列表、分页和结果类型。
- 使用条件类型、映射类型和工具类型解决真实复用问题。
- 使用类型守卫缩小 `unknown`。
- 使用 discriminated union 表达异步状态。

### 阶段三：高级

- 编写模块声明和最小第三方类型补丁。
- 解释 ESM、CJS、模块解析和路径 alias。
- 设计可发布的类型声明和 API。
- 完成 JavaScript 到 strict TypeScript 的迁移计划。

### 阶段四：React 实战

- 完成类型安全的组件、表单、路由和 API 层。
- 使用运行时 schema 校验外部数据。
- 为权限、错误和异步状态建立类型模型。
- 通过 lint、类型检查、测试和构建门禁。

## 2. 排错题

- `any` 扩散导致错误延迟到运行时。
- `unknown` 未缩小就访问属性。
- 可选属性与 `undefined` 的严格检查冲突。
- 数组索引在 `noUncheckedIndexedAccess` 下产生错误。
- ESM/CJS 导入形式不一致。
- 路径 alias 在编辑器、测试和构建工具中行为不同。
- 第三方库类型声明与实际运行时 API 不一致。
- 联合类型新增成员后，switch 未完成穷尽处理。

## 4. 项目评审问题

- 这个类型表达了业务约束还是只描述了当前数据形状？
- 为什么这里使用联合类型而非可选属性？
- 外部数据进入系统后在哪里被校验？
- 哪些数据可以信任，哪些数据必须视为 `unknown`？
- 类型修改后，编译器能否覆盖所有调用方？
- 这个泛型提高了复用性还是增加了理解成本？
- `any`、类型断言和声明补丁分别解决什么问题？
- 如何保证类型声明与运行时行为一致？
